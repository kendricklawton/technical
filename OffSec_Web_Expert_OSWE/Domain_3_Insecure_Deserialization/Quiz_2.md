# Domain 3 — Quiz 2: Java & .NET Gadget Chains

> White-box scenarios. Answer before expanding.

---

**Q1.** A Java endpoint calls `new ObjectInputStream(req.getInputStream()).readObject()`. Your first white-box step toward RCE is:

- A. Check the dependencies for a gadget library (e.g. Commons-Collections) and match a ysoserial chain.
- B. Brute-force serialized bytes until one triggers execution.
- C. Switch the endpoint to JSON so typing is disabled.
- D. Decompile the JVM itself to find a gadget.

<details><summary>Show Answer & Explanation</summary>

**A.** `readObject` on untrusted input is the sink; the remaining question is which gadget is on the classpath, which the dependency list answers, letting you pick a ysoserial chain. Brute force (B) is infeasible; changing the endpoint (C) is a fix, not an exploit; the JVM (D) is not where app gadgets live.
</details>

**Q2.** Why does the `TemplatesImpl` gadget achieve code execution during deserialization?

- A. It carries attacker-supplied compiled bytecode that executes when the object is instantiated.
- B. It decrypts the application's secret key and logs in as admin.
- C. It overflows the deserialization buffer to redirect execution.
- D. It opens a JDWP debugger port the attacker connects to.

<details><summary>Show Answer & Explanation</summary>

**A.** `TemplatesImpl` holds bytecode (`_bytecodes`) that the JVM loads and runs on instantiation, so deserialising it executes attacker code. It is not key decryption (B), a buffer overflow (C), or a debugger trick (D).
</details>

**Q3.** Source shows Jackson configured with `enableDefaultTyping()` deserialising request JSON. Why is this dangerous?

- A. The JSON can specify arbitrary types to instantiate, enabling gadget classes to reach execution.
- B. Jackson always disables type checks, so all JSON is executed as code.
- C. Default typing encrypts the payload, hiding the attack from logs.
- D. It only affects performance, not security.

<details><summary>Show Answer & Explanation</summary>

**A.** Polymorphic/default typing lets the input choose the concrete type (`@class`/`$type`-style), so an attacker names a gadget type that executes. It does not execute all JSON (B), encrypt anything (C), or affect only performance (D).
</details>

**Q4.** A .NET app deserialises request JSON with `TypeNameHandling.Auto`. Which ysoserial.net gadget commonly reaches command execution here?

- A. `ObjectDataProvider`, which can be made to invoke `Process.Start`.
- B. `CommonsCollections6`, the standard Java chain.
- C. `pickle.__reduce__`, the Python reduce gadget.
- D. `node-serialize`, the JavaScript function gadget.

<details><summary>Show Answer & Explanation</summary>

**A.** `ObjectDataProvider` is a .NET gadget that invokes arbitrary methods such as `Process.Start`, generated by ysoserial.net for `Json.Net`. The others are Java (B), Python (C), and Node (D) gadgets.
</details>

**Q5.** ViewState MAC validation is enabled, so a naive forged `__VIEWSTATE` is rejected. What dependency unlocks a forged-ViewState RCE?

- A. The `machineKey` (validationKey/decryptionKey), e.g. leaked via LFI/SQLi reading web.config.
- B. The server's TLS private key, which signs ViewState.
- C. The user's session cookie, which replaces the MAC.
- D. Nothing; MAC-protected ViewState can never be forged.

<details><summary>Show Answer & Explanation</summary>

**A.** With the `machineKey`, you can compute a valid MAC for a malicious ViewState (ysoserial.net), so a leaked key (via config disclosure) unlocks it. The TLS key (B) and session cookie (C) do not sign ViewState; forging is possible with the key (D is false).
</details>

**Q6.** Why is `BinaryFormatter.Deserialize` on request data a finding even without a known public gadget in your notes?

- A. It reconstructs arbitrary typed graphs from untrusted input, which is inherently unsafe and gadget-rich.
- B. It is safe unless the data is larger than 1 MB.
- C. It only deserialises primitive types, so it cannot execute code.
- D. It validates a MAC by default, so it is secure.

<details><summary>Show Answer & Explanation</summary>

**A.** `BinaryFormatter` is documented as dangerous for untrusted data because it rebuilds arbitrary types; gadgets are plentiful (ysoserial.net). Size (B) is irrelevant; it handles complex types (C is false); it has no inherent MAC (D).
</details>

**Q7.** For the exploit script against a Java `readObject` sink, how should payload generation be handled?

- A. Invoke ysoserial (or embed the bytes) inside the script to produce the chosen chain, then deliver it deterministically.
- B. Require the grader to run ysoserial by hand and paste the output.
- C. Generate a random serialized blob each run for unpredictability.
- D. Use sqlmap to produce the Java object.

<details><summary>Show Answer & Explanation</summary>

**A.** The single-command script generates (or embeds) the exact ysoserial payload and sends it. Manual steps (B) break automation; randomness (C) is counterproductive; sqlmap (D) is unrelated.
</details>

---

**Q8.** Which remediation set correctly addresses the Java/.NET sinks in this quiz?

- A. Avoid native binary deserialisers on untrusted input, disable polymorphic typing, apply serialization allow-list filters, and protect/rotate ViewState keys.
- B. Compress serialized data so gadgets cannot be embedded.
- C. Move deserialization to a background thread so exploits time out.
- D. Obfuscate class names so ysoserial cannot reference them.

<details><summary>Show Answer & Explanation</summary>

**A.** Do not deserialise untrusted data with `BinaryFormatter`/`readObject`; disable default typing, use JEP 290-style allow-lists, keep MAC on and keys secret/rotated. Compression (B), threading (C), and obfuscation (D) do not address the root cause.
</details>
