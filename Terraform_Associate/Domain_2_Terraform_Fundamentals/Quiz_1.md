### Question 10 (Objective 2d)

- A. It does not; removing a resource block from `.tf` files simply orphans the resource in AWS.

## Answer Key & Rationales

1. **B** — The pessimistic operator `~> 6.12.0` allows only the rightmost segment (the patch version) to increment: `>= 6.12.0` and `< 6.13.0`.
2. **D** — `~> 6.12` allows the minor segment to increment (`>= 6.12.0, < 7.0.0`), whereas `~> 6.12.0` restricts upgrades to patch versions (`>= 6.12.0, < 6.13.0`).
3. **D** — By default, `terraform init` honors the version pinned in `.terraform.lock.hcl` (`5.70.0`). Running `terraform init -upgrade` selects the newest version allowed by configuration constraints (`5.75.0`) and updates `.terraform.lock.hcl`.
4. **C** — **Official** providers are maintained by HashiCorp; **Partner** providers are maintained by verified technology partners; **Community** providers are maintained by individual contributors.
5. **A** — The `provider` meta-argument takes an unquoted reference `<PROVIDER>.<ALIAS>` (`provider = aws.eu_central`).
6. **A** — Child modules receive provider configurations via the `providers = { <CHILD_PROVIDER> = <PARENT_PROVIDER>.<ALIAS> }` map argument.
7. **C** — Commit `.tf` files and `.terraform.lock.hcl`. Always exclude `.terraform/` (large binaries), `*.tfstate*` (contains sensitive plaintext data), and secret `.tfvars` files.
8. **A** — State provides the 1:1 mapping between logical HCL addresses and real-world cloud IDs, tracks dependencies (especially for deleted resources), and caches attributes.
9. **C** — Setting `TF_PLUGIN_CACHE_DIR` or `plugin_cache_dir` in `.terraformrc` / `terraform.rc` caches downloaded provider plugins in a central directory.
10. **B** — Because the resource block was deleted from `.tf` files, only the **state file** retains the record that `aws_eip.nat` (`eipalloc-0123456789abcdef0`) was managed by Terraform and must now be destroyed.
