## 1. AWS CloudFormation Internals & Lifecycle

### 1.1 `CreationPolicy` vs. `WaitCondition`
When CloudFormation launches an EC2 instance or Auto Scaling Group, the resource status normally transitions to `CREATE_COMPLETE` as soon as the hypervisor reports the VM is `running`—**long before** `UserData` scripts or `cfn-init` finish installing packages and starting the web server. To pause stack progression until the application inside the instance is genuinely ready:

* **Supported Resources**
  * **`CreationPolicy` (`ResourceSignal`):** **ONLY** `AWS::EC2::Instance`, `AWS::AutoScaling::AutoScalingGroup`, and `AWS::AppStream::Fleet`.
  * **`AWS::CloudFormation::WaitCondition` + `WaitConditionHandle`:** **Any resource** or external on-premises/hybrid workflow.
* **Signaling Mechanism**
  * **`CreationPolicy` (`ResourceSignal`):** `cfn-signal -e $? --stack ${AWS::StackName} --resource WebServerASG --region ${AWS::Region}` (Requires IAM `cloudformation:SignalResource` permission on the EC2 Instance Profile).
  * **`AWS::CloudFormation::WaitCondition` + `WaitConditionHandle`:** `cfn-signal -e $? "${WaitConditionHandle}"` or `curl -X PUT` to the **Pre-Signed S3 URL** generated by `WaitConditionHandle` (**No IAM permissions required** to signal!).
* **Update Support**
  * **`CreationPolicy` (`ResourceSignal`):** Automatically works alongside `UpdatePolicy` (`WaitOnResourceSignals: true`) during ASG rolling updates.
  * **`AWS::CloudFormation::WaitCondition` + `WaitConditionHandle`:** `WaitCondition` only runs on **Create** unless replaced by changing the logical ID of the `WaitCondition` resource on every update.

#### Complete `CreationPolicy` vs. `WaitCondition` YAML Comparison
```yaml
Resources:
  # Pattern A: Native CreationPolicy on an Auto Scaling Group (Recommended for EC2/ASG)
  AppServerASG:
    Type: AWS::AutoScaling::AutoScalingGroup
    CreationPolicy:
      ResourceSignal:
        Count: 3           # Number of positive signals required before CREATE_COMPLETE
        Timeout: PT15M     # ISO-8601 duration (Max: PT12H)
      AutoScalingCreationPolicy:
        MinSuccessfulInstancesPercent: 100
    Properties:
      MinSize: '3'
      MaxSize: '6'
      DesiredCapacity: '3'
      VPCZoneIdentifier:
        - !Ref PrivateSubnet1
        - !Ref PrivateSubnet2
      LaunchTemplate:
        LaunchTemplateId: !Ref AppLaunchTemplate
        Version: !GetAtt AppLaunchTemplate.LatestVersionNumber

  # Pattern B: WaitCondition + WaitConditionHandle (Used for Non-EC2 or External Hybrid Signalling)
  DatabaseMigrationWaitHandle:
    Type: AWS::CloudFormation::WaitConditionHandle

  DatabaseMigrationWaitCondition:
    Type: AWS::CloudFormation::WaitCondition
    DependsOn: OnPremMigrationRunner
    Properties:
      Handle: !Ref DatabaseMigrationWaitHandle
      Timeout: '1800' # Seconds (String value, unlike CreationPolicy ISO-8601)
      Count: 1
```

#### Raw HTTP `PUT` Payload for `WaitConditionHandle` (Zero AWS CLI / IAM Required)
When signaling a `WaitConditionHandle` pre-signed URL directly via `curl` from an on-premises server or container without `cfn-signal`:
```bash
curl -X PUT -H 'Content-Type:' \
  --data-binary '{
    "Status": "SUCCESS",
    "Reason": "Database schema migration v4.2 completed",
    "UniqueId": "migration-node-01",
    "Data": "RowsMigrated=145020"
  }' \
  "${WaitConditionHandleUrl}"
```

### 1.2 `UpdatePolicy` Deep Dive
`UpdatePolicy` controls how CloudFormation handles updates to **Auto Scaling Groups**, **ElastiCache Replication Groups**, and **OpenSearch Domains**.

* **`AutoScalingRollingUpdate`:** Replaces instances in batches inside the **same** Auto Scaling Group:
  * `MinInstancesInService`: Minimum number of instances that must remain healthy and in service at all times. (e.g., if `DesiredCapacity: 10` and `MinInstancesInService: 8`, at most 2 instances can be taken out of service at a time unless `MaxSize` allows scaling out temporary instances first).
  * `MaxBatchSize`: Maximum number of instances CloudFormation updates in a single batch.
  * `WaitOnResourceSignals: true`: Forces CloudFormation to wait for a `cfn-signal` from each newly launched instance in the batch before moving to the next batch.
  * `PauseTime: PT10M`:
    * When `WaitOnResourceSignals: true`, `PauseTime` is the **maximum timeout window** within which the new instances in the batch must send their `cfn-signal` (otherwise the update fails and rolls back!).
    * When `WaitOnResourceSignals: false`, `PauseTime` is simply a fixed sleep duration between batches.
  * `SuspendProcesses`: Always suspend `[HealthCheck, ReplaceUnhealthy, AZRebalance, AlarmNotification, ScheduledActions]` during a rolling update so native ASG scaling or AZ rebalancing does not interfere with CloudFormation's batch replacement!
* **`AutoScalingReplacingUpdate` (`WillReplace: true`):**
  * Creates a **brand-new Auto Scaling Group** alongside the old one (Blue/Green style).
  * Waits for the new ASG to pass `CreationPolicy` signals.
  * Only deletes the old ASG after the new ASG reaches `CREATE_COMPLETE`. If the new ASG fails `CreationPolicy`, the old ASG remains untouched!
* **`AutoScalingScheduledAction` (`IgnoreUnmodifiedGroupSizeProperties: true`):**
  * Prevents CloudFormation stack updates from overwriting the current `DesiredCapacity` if an Auto Scaling Scheduled Action or Target Tracking Scaling Policy has changed the group size since the last stack deployment.
* **`EnableVersionUpgrade: true` (OpenSearch Service):**
  * Performs an in-place OpenSearch/Elasticsearch version upgrade without replacing the domain resource.

```yaml
  ProductionWebASG:
    Type: AWS::AutoScaling::AutoScalingGroup
    UpdatePolicy:
      AutoScalingScheduledAction:
        IgnoreUnmodifiedGroupSizeProperties: true
      AutoScalingRollingUpdate:
        MinInstancesInService: 8
        MaxBatchSize: 2
        PauseTime: PT10M
        WaitOnResourceSignals: true
        MinSuccessfulInstancesPercent: 100
        SuspendProcesses:
          - HealthCheck
          - ReplaceUnhealthy
          - AZRebalance
          - AlarmNotification
          - ScheduledActions
```

### 1.3 `DeletionPolicy` & `UpdateReplacePolicy`
* **`DeletionPolicy`:** Controls what happens to a physical resource when its logical resource is removed from the template or the entire stack is deleted.
* **`UpdateReplacePolicy`:** Controls what happens to the **old physical resource** when a stack update requires **Replacement** (`Requires: Replacement`, such as changing an RDS `DBInstanceIdentifier` or EC2 `AvailabilityZone`).
  * **Exam Trap:** Setting `DeletionPolicy: Retain` does **NOT** protect a resource from being deleted during a stack **Update Replacement**! You must also set **`UpdateReplacePolicy: Retain`** (or `Snapshot`).

* **`Delete`** (Default)
  * **Behavior:** Deletes the physical resource. (Note: Fails on non-empty S3 buckets or ECR repos without `EmptyOnDelete`).
  * **Supported Resources:** All resources.
* **`Retain`**
  * **Behavior:** Leaves the physical resource running in the AWS account unmanaged by CloudFormation.
  * **Supported Resources:** All resources.
* **`RetainExceptOnCreate`**
  * **Behavior:** Retains the resource on subsequent deletes, **unless** the delete is caused by a rollback of the initial resource creation!
  * **Supported Resources:** All resources.
* **`Snapshot`**
  * **Behavior:** Creates a final backup snapshot before deleting the resource.
  * **Supported Resources:** `AWS::EC2::Volume`, `AWS::RDS::DBInstance`, `AWS::RDS::DBCluster` (cluster-level), `AWS::ElastiCache::CacheCluster`, `AWS::Redshift::Cluster`.

```yaml
  ProductionDatabaseCluster:
    Type: AWS::RDS::DBCluster
    DeletionPolicy: Snapshot
    UpdateReplacePolicy: Snapshot
    Properties:
      Engine: aurora-postgresql
      DatabaseName: prodledger
      StorageEncrypted: true
```

### 1.4 CloudFormation Helper Scripts (`cfn-init`, `cfn-hup`, `cfn-signal`, `cfn-get-metadata`)

#### Exact Execution Order of `AWS::CloudFormation::Init` Metadata Sections
When `cfn-init` executes a `config` block inside `AWS::CloudFormation::Init`, it processes the 7 keys in this **fixed, immutable sequence** regardless of how they are ordered in your YAML file:

```text
========================================================================================
                 AWS CloudFormation cfn-init Metadata Execution Order
========================================================================================

  1. packages ──► 2. groups ──► 3. users ──► 4. sources
  (rpm, yum, apt,     (OS User        (OS Users,       (Download & extract
   python, gems)       Groups)         UIDs, homes)     tar/zip archives)
                                                              │
  ┌───────────────────────────────────────────────────────────┘
  ▼
  5. files ──► 6. commands ──► 7. services
  (Write inline      (Execute shell commands       (sysvinit / systemd
   files or S3)       in ALPHABETICAL order!)       enable & start services)
```

> **Exam Pro-Tip:** If you need to run a shell command **before** `packages` are installed (e.g., adding a custom yum repository or EPEL), you cannot do that inside a single `config` block because `packages` (1) always runs before `commands` (6). Instead, split your configuration into multiple named configs and chain them in an ordered **`configSets`** list!

#### Complete `AWS::CloudFormation::Init` + `cfn-hup` Live Reload Configuration
* Changing the `Metadata` block of an `AWS::EC2::Instance` or `AWS::AutoScaling::LaunchTemplate` does **not** automatically execute anything on already-running EC2 instances.
* The **`cfn-hup` daemon** runs in the background on the EC2 instance (configured via `/etc/cfn/cfn-hup.conf` and `/etc/cfn/hooks.d/cfn-auto-reloader.conf`), polls CloudFormation every $N$ minutes (default `interval=15`, minimum `1`), detects changes in the `AWS::CloudFormation::Init` metadata, and executes `action=/opt/aws/bin/cfn-init -v --stack ...` to apply the updated configuration in-place without instance replacement.

```yaml
  AppLaunchTemplate:
    Type: AWS::EC2::LaunchTemplate
    Metadata:
      AWS::CloudFormation::Init:
        configSets:
          full_install:
            - "01_setup_cfn_hup"
            - "02_install_app"
        01_setup_cfn_hup:
          files:
            /etc/cfn/cfn-hup.conf:
              content: !Sub |
                [main]
                stack=${AWS::StackId}
                region=${AWS::Region}
                interval=1
                verbose=true
              mode: "000400"
              owner: root
              group: root
            /etc/cfn/hooks.d/cfn-auto-reloader.conf:
              content: !Sub |
                [cfn-auto-reloader-hook]
                triggers=post.update
                path=Resources.AppLaunchTemplate.Metadata.AWS::CloudFormation::Init
                action=/opt/aws/bin/cfn-init -v --stack ${AWS::StackName} --resource AppLaunchTemplate --configsets full_install --region ${AWS::Region}
                runas=root
              mode: "000400"
              owner: root
              group: root
          services:
            sysvinit:
              cfn-hup:
                enabled: true
                ensureRunning: true
                files:
                  - /etc/cfn/cfn-hup.conf
                  - /etc/cfn/hooks.d/cfn-auto-reloader.conf
        02_install_app:
          packages:
            yum:
              httpd: []
          files:
            /var/www/html/index.html:
              content: !Sub "<h1>Environment: ${EnvironmentName} - Version ${AppVersion}</h1>"
              mode: "000644"
          commands:
            01_validate_apache_syntax:
              command: "apachectl configtest"
            02_set_selinux_bool:
              command: "setsebool -P httpd_can_network_connect 1 || true"
          services:
            sysvinit:
              httpd:
                enabled: true
                ensureRunning: true
                files:
                  - /var/www/html/index.html
    Properties:
      LaunchTemplateData:
        ImageId: !Ref LatestAmiId
        InstanceType: m6i.large
        UserData:
          Fn::Base64: !Sub |
            #!/bin/bash -x
            /opt/aws/bin/cfn-init -v \
              --stack ${AWS::StackName} \
              --resource AppLaunchTemplate \
              --configsets full_install \
              --region ${AWS::Region}
            # Signal CloudFormation with the exit status ($?) of cfn-init!
            /opt/aws/bin/cfn-signal -e $? \
              --stack ${AWS::StackName} \
              --resource ProductionWebASG \
              --region ${AWS::Region}
```

### 1.5 CloudFormation Custom Resources (`AWS::CloudFormation::CustomResource` / `Custom::*`)
Custom Resources allow CloudFormation to manage non-AWS resources or execute imperative provisioning logic (e.g., emptying an S3 bucket on `Delete`, running RDS schema bootstrap, looking up dynamic CIDR allocations in IPAM, or registering webhooks in GitHub/Datadog).

```text
========================================================================================
           CloudFormation Custom Resource Asynchronous Response Protocol
========================================================================================

  [ AWS CloudFormation ]
            │
            │ 1. Invoke Lambda (RequestType: Create|Update|Delete, ResponseURL, StackId)
            ▼
  [ Custom Resource Lambda ]
            │
            │ 2. Execute Custom Logic (Wrapped in try/except to prevent 1-hour freeze!)
            │
            │ 3. HTTP PUT Signed JSON Payload:
            │    {
            │      "Status": "SUCCESS" | "FAILED",
            │      "PhysicalResourceId": "my-resource-id",
            │      "StackId": "arn:aws:cloudformation:...",
            │      "RequestId": "req-12345",
            │      "Data": { "Key": "Value" }
            │    }
            ▼
  [ Pre-Signed S3 ResponseURL ]
            │
            │ 4. CloudFormation detects S3 PUT completion & resumes stack
            ▼
  [ AWS CloudFormation: Complete / Rollback ]
```

#### Critical Custom Resource Internals & Exam Traps
1. **Why Unhandled Exceptions Hang Stacks for 1 Hour:**
   * CloudFormation does **not** watch the Lambda execution return value! It waits asynchronously for an HTTP `PUT` request to the **S3 Pre-Signed `ResponseURL`** included in the event payload.
   * If your Lambda throws an unhandled syntax/runtime exception or times out (`Task timed out after X seconds`) before sending an HTTP `PUT` (`Status: "FAILED"`) to `ResponseURL`, CloudFormation waits up to **1 hour** (or the custom `ServiceTimeout` value, configurable from 1 to 3600 seconds) before timing out and rolling back!
   * **Defense:** Always wrap your Lambda handler in a top-level `try...except Exception:` block AND register a `threading.Timer` firing 1–2 seconds before `context.get_remaining_time_in_millis()` to guarantee `cfnresponse.send(event, context, cfnresponse.FAILED, ...)` is called.
2. **The `PhysicalResourceId` Replacement Rule (Heavily Tested):**
   * On **`Create`**, your Custom Resource returns a `PhysicalResourceId` (e.g., `"s3-cleanup-my-bucket"`).
   * On **`Update`**, if your Custom Resource returns the **exact same `PhysicalResourceId`**, CloudFormation treats it as an **in-place update** and completes normally.
   * On **`Update`**, if your Custom Resource returns a **DIFFERENT `PhysicalResourceId`** (e.g., you generated a random `uuid.uuid4()` on every invocation!), CloudFormation assumes the resource was **replaced** and immediately sends a **`Delete` request passing the OLD `PhysicalResourceId`** during the `UPDATE_CLEANUP_IN_PROGRESS` phase! If your `Delete` handler deletes the underlying resource based on that ID, you will accidentally destroy your live resource during a routine update!
3. **Handling `Delete` Requests Safely:**
   * Your `Delete` handler **must be idempotent**. Even if the underlying external resource was already manually deleted (`ResourceNotFoundException`), the `Delete` handler should catch the error and return `Status: "SUCCESS"` to `ResponseURL`. If a `Delete` handler returns `FAILED`, the stack gets stuck in `DELETE_FAILED`!
4. **SNS-Backed vs. Lambda-Backed Custom Resources:**
   * **Lambda-Backed:** `ServiceToken` is a Lambda Function ARN. Best for serverless, self-contained AWS automation (< 15 minutes).
   * **SNS-Backed:** `ServiceToken` is an SNS Topic ARN (which can fan out to an SQS queue polled by EC2/on-premises workers or Step Functions). Required when a custom provisioning job takes **longer than 15 minutes** (up to 1 hour `ServiceTimeout`) or must run inside an on-premises network without inbound connectivity.

### 1.6 CloudFormation Macros vs. Transforms
* **Transforms** preprocess template snippets into standard CloudFormation JSON/YAML during the Change Set creation phase before deployment:
  * **`AWS::Serverless-2016-10-31`:** Expands AWS SAM templates into standard CloudFormation resources.
  * **`AWS::Include`:** Fetches external YAML/JSON boilerplate snippets stored in Amazon S3 and injects them inline (can be used at top-level `Transform:` or inside `Fn::Transform`).
  * **`AWS::LanguageExtensions`:** Built-in transform enabling advanced intrinsic functions such as **`Fn::ForEach`** (dynamically generating resources/properties in loops), `Fn::Length`, and `Fn::ToJsonString`.
* **CloudFormation Macros (`AWS::CloudFormation::Macro`):**
  * Backed by an **AWS Lambda function** in your account.
  * Receives the parsed JSON template fragment (`event["fragment"]`), `templateParameterValues`, and `params`.
  * Returns `{"requestId": event["requestId"], "status": "success", "fragment": modified_fragment}`.
  * **Macro vs. Custom Resource Decision Rule:**
    * Use a **Macro** when you want to **transform, validate, or generate CloudFormation template syntax** *before* CloudFormation provisions resources (e.g., automatically injecting standard `Tags`, `KmsKeyId`, or `DeletionPolicy: Retain` onto every resource in a template).
    * Use a **Custom Resource** when you need to execute **imperative API calls or side effects** *during* stack creation/update/deletion.

#### Example 1: Using `AWS::LanguageExtensions` and `Fn::ForEach`
```yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: 'AWS::LanguageExtensions'

Resources:
  'Fn::ForEach::Topics':
    - TopicName
    - [Orders, Billing, Shipments]
    - '${TopicName}Topic':
        Type: 'AWS::SNS::Topic'
        Properties:
          TopicName: !Sub 'prod-${TopicName}-events'
          KmsMasterKeyId: alias/aws/sns
```

#### Example 2: CloudFormation Macro Lambda Auto-Injecting Encryption & Tags
```python
import copy

def lambda_handler(event, context):
    fragment = copy.deepcopy(event["fragment"])
    resources = fragment.get("Resources", {})

    for logical_id, resource in resources.items():
        res_type = resource.get("Type")
        props = resource.setdefault("Properties", {})

        # Automatically enforce KMS encryption on all S3 buckets in any template using this Macro
        if res_type == "AWS::S3::Bucket":
            props.setdefault(
                "BucketEncryption",
                {
                    "ServerSideEncryptionConfiguration": [
                        {"ServerSideEncryptionByDefault": {"SSEAlgorithm": "aws:kms"}}
                    ]
                },
            )
            props.setdefault(
                "PublicAccessBlockConfiguration",
                {
                    "BlockPublicAcls": True,
                    "BlockPublicPolicy": True,
                    "IgnorePublicAcls": True,
                    "RestrictPublicBuckets": True,
                },
            )

    return {
        "requestId": event["requestId"],
        "status": "success",
        "fragment": fragment,
    }
```

### 1.7 Drift Detection & Resource Import
* **Drift Detection:** Compares the stack's expected template configuration against the actual live configuration of resources in AWS.
  * Statuses: `IN_SYNC`, `MODIFIED`, `DELETED`, `NOT_CHECKED`.
  * **Exam Caveat:** Drift Detection only inspects properties explicitly defined in the stack template (or default values of those properties), and not every CloudFormation resource type supports drift detection.
* **Remediating Drift or Importing Unmanaged Resources (`ResourceImport` Change Set):**
  * If an administrator manually modified a resource out-of-band (or created a resource manually in the Console) and you want to bring the stack back in sync without destroying the resource:
    1. **Detach / Retain:** If the resource is already in the stack but severely drifted, set `DeletionPolicy: Retain` on the resource, remove it from the template, update the stack (this detaches the resource without deleting it), and then **Import** it back with matching properties!
    2. **Resource Import Requirements:**
       * Every resource being imported **MUST** have **`DeletionPolicy: Retain`** explicitly declared in the template.
       * You must provide the unique physical identifier for each imported resource (e.g., `BucketName`, `DBInstanceIdentifier`, `TableName`).
       * You cannot modify or create other existing resources in the same `IMPORT` Change Set operation.
       * The imported resource cannot already belong to another CloudFormation stack.

```bash
# Step 1: Create an IMPORT Change Set
aws cloudformation create-change-set \
  --stack-name ProdStorageStack \
  --change-set-name ImportLegacyS3Bucket \
  --change-set-type IMPORT \
  --template-body file://template-with-retain.yaml \
  --resources-to-import '[
    {
      "ResourceType": "AWS::S3::Bucket",
      "LogicalResourceId": "LegacyAuditBucket",
      "ResourceIdentifier": {
        "BucketName": "acme-prod-legacy-audit-logs"
      }
    }
  ]'

# Step 2: Execute the IMPORT Change Set
aws cloudformation execute-change-set \
  --stack-name ProdStorageStack \
  --change-set-name ImportLegacyS3Bucket
```

### 1.8 Cross-Stack References (`Export` / `Fn::ImportValue`) vs. Nested Stacks vs. SSM Parameter Store

* **Cross-Stack References**
  * **Mechanism:** Stack A declares `Outputs` with `Export: Name: SharedVpcId`. Stack B calls `Fn::ImportValue: SharedVpcId`.
  * **Lifecycle Coupling & Update Behavior:** **Tightly Locked!** While Stack B imports `SharedVpcId`, **Stack A CANNOT delete or modify the value of `SharedVpcId`**! Any attempt to update Stack A to output a new VPC ID fails with `Export SharedVpcId cannot be updated as it is in use by StackB`.
  * **Best Use Case:** Foundational, immutable shared infrastructure (VPC IDs, Subnet IDs) managed by different teams inside the same account/region.
* **SSM Parameter Store Decoupling**
  * **Mechanism:** Stack A creates an `AWS::SSM::Parameter` (`/network/vpc-id`). Stack B uses a Dynamic Reference `{{resolve:ssm:/network/vpc-id}}` or `AWS::SSM::Parameter::Value<String>`.
  * **Lifecycle Coupling & Update Behavior:** **Loosely Coupled!** Stack A can update `/network/vpc-id` at any time without being blocked by Stack B.
  * **Best Use Case:** Frequently updated shared values (AMI IDs, security group IDs, endpoints) across stacks.
* **Nested Stacks (`AWS::CloudFormation::Stack`)**
  * **Mechanism:** Root stack passes values down via `Parameters` and reads child outputs via `!GetAtt ChildStack.Outputs.Val`.
  * **Lifecycle Coupling & Update Behavior:** **Single Lifecycle Unit:** Updating the root stack updates all modified child stacks atomically.
  * **Best Use Case:** Breaking up massive templates that exceed CloudFormation limits (max 500 resources per template, 1 MB S3 template size) within a single application boundary.

#### How to Safely Update or Remove a Locked `Export` Used by `Fn::ImportValue`
If Stack A exports `OldSecurityGroup` and Stack B imports it via `!ImportValue OldSecurityGroup`, and you want to replace `OldSecurityGroup` with `NewSecurityGroup`:
1. Update **Stack A** to create `NewSecurityGroup` while **keeping `OldSecurityGroup` and its `Export`** temporarily in Stack A.
2. Update **Stack B** to replace `!ImportValue OldSecurityGroup` with the new export (or an SSM Parameter).
3. Once zero stacks import `OldSecurityGroup`, update **Stack A** to remove `OldSecurityGroup` and its `Export`.

### 1.9 CloudFormation StackSets (`SELF_MANAGED` vs. `SERVICE_MANAGED`)
StackSets deploy a common CloudFormation template across multiple AWS Accounts and multiple AWS Regions from a single administrator account.

* **IAM Roles Required**
  * **`SELF_MANAGED` Permissions:** **Manual Setup:** You must create `AWSCloudFormationStackSetAdministrationRole` in the Admin Account and `AWSCloudFormationStackSetExecutionRole` in **every Target Account**.
  * **`SERVICE_MANAGED` Permissions (AWS Organizations):** **Zero Manual IAM Setup:** Uses AWS Organizations Service-Linked Roles (`AWSServiceRoleForCloudFormationStackSetsOrgAdmin` and `...OrgParent`).
* **Deployment Target**
  * **`SELF_MANAGED` Permissions:** Specific AWS Account IDs (`["222222222222", "333333333333"]`).
  * **`SERVICE_MANAGED` Permissions (AWS Organizations):** **Root Organization (`r-xxxx`)** or **Organizational Units (`ou-xxxx`)** (plus optional account filters: `INTERSECTION`, `DIFFERENCE`, `UNION`).
* **Auto-Deployment**
  * **`SELF_MANAGED` Permissions:** **NO.** New accounts must be added manually.
  * **`SERVICE_MANAGED` Permissions (AWS Organizations):** **YES (`AutoDeployment: Enabled: true`)!** Automatically deploys stack instances when a new account joins the OU, and deletes/retains stack instances when an account leaves (`RetainStacksOnAccountRemoval: true | false`).
* **Delegated Administrator**
  * **`SELF_MANAGED` Permissions:** Any account with the Admin IAM Role.
  * **`SERVICE_MANAGED` Permissions (AWS Organizations):** Management Account can register up to **5 Member Accounts** as **Delegated Administrators** (e.g., Security Tooling Account) so you don't run StackSets from the Management Account.

#### StackSet Operation Preferences (Concurrency & Fault Tolerance)
* **`RegionConcurrencyType`:** `SEQUENTIAL` (default—deploys one region completely before moving to the next region) or **`PARALLEL`** (deploys to all target regions simultaneously).
* **`MaxConcurrentCount` / `MaxConcurrentPercentage`:** Maximum number of target accounts in which StackSets deploys concurrently per region. (Speeds up deployment).
* **`FailureToleranceCount` / `FailureTolerancePercentage`:** Maximum number of accounts per region in which the stack operation can fail before CloudFormation halts the entire StackSet operation and stops deploying to remaining accounts/regions.
  * **Exam Rule:** If a question asks to "maximize deployment speed across 100 accounts and 4 regions while tolerating up to 5% failures," choose **`RegionConcurrencyType: PARALLEL`**, **`MaxConcurrentPercentage: 100`**, and **`FailureTolerancePercentage: 5`**.

### 1.10 CloudFormation Guard (`cfn-guard`) & CloudFormation Hooks
* **AWS CloudFormation Guard (`cfn-guard`):**
  * Open-source, fast CLI Policy-as-Code tool written in Rust that validates CloudFormation templates, Terraform JSON plans, and Kubernetes manifests against declarative compliance rules in CI/CD (CodeBuild) or pre-commit hooks.
* **AWS CloudFormation Hooks:**
  * Proactive server-side enforcement invoked by the CloudFormation engine **right before** a resource `CREATE`, `UPDATE`, or `DELETE` action occurs (`TargetPoint: PRE_PROVISION`).
  * Supports **`AWS::EarlyValidation::PropertyValidation`**, **Guard Hooks** (`AWS::Guard::Hook` running `cfn-guard` rules server-side inside CloudFormation!), and **Lambda Hooks**.
  * `FailureMode: FAIL` blocks non-compliant stack operations across the account regardless of whether the user deployed via Console, CLI, CDK, or CodePipeline; `FailureMode: WARN` logs a warning to CloudWatch/EventBridge and allows the deployment to proceed.

#### Example `cfn-guard` Rule Enforcing Encrypted GP3 EBS Volumes & Non-Public S3 Buckets
```ruby
# rules/security_baseline.guard
let s3_buckets = Resources.*[ Type == 'AWS::S3::Bucket' ]
let ebs_volumes = Resources.*[ Type == 'AWS::EC2::Volume' ]

rule enforce_s3_encryption_and_public_block when %s3_buckets !empty {
```

### 1.11 AWS CloudFormation Git Sync (Native GitOps for CloudFormation)

CloudFormation Git Sync provides native, serverless GitOps synchronization directly from source control (GitHub, GitHub Enterprise, GitLab, Bitbucket) to CloudFormation stacks without needing CodePipeline, Jenkins, or external CI/CD runner infrastructure.

```text
========================================================================================
                      CloudFormation Git Sync Deployment Pipeline
========================================================================================

  [ Developer PR Merged ]
             │
             ▼
  [ Git Repository (GitHub / GitLab / Bitbucket) ]
             │
             │ (Webhook Event)
             ▼
  [ AWS CodeConnections (Git Sync Trigger) ]
             │
             ▼
  [ CloudFormation Git Sync (Generates Change Set) ]
             │
             │ (sts:AssumeRole)
             ▼
  [ Deployment IAM Role (Execution Role) ]
             │
             ▼
  [ CloudFormation Stack Resources Provisioned ]
```

#### Core Components & Mechanics
- **AWS CodeConnections (formerly CodeStar Connections):** Secure OAuth / app-based connection between AWS and the Git provider.
- **Deployment Definition File (`deployment-definition.yaml` or stack configuration file):**
  - Stored inside the Git repository alongside the CloudFormation template.
  - Declares the template path, parameter values/SSM dynamic references, stack name, and IAM deployment role.
- **IAM Deployment Role:** Assumed by CloudFormation (`cloudformation.amazonaws.com`) to provision the actual stack resources. Must have necessary service permissions plus `iam:PassRole` where needed.
- **Change Set Workflow:**
  - Git Sync can be configured to **automatically create and execute** change sets upon commits to the monitored branch.
  - Or it can create change sets and publish status comments to pull requests, allowing developers to review planned infrastructure changes before merging.

#### Sample Git Sync Deployment Definition (`deployment-definition.yaml`)
```yaml
target-environments:
  - name: production
    template-file-path: infrastructure/vpc-and-clusters.yaml
    parameters:
      EnvironmentName: production
      VpcCidrBlock: 10.0.0.0/16
      EnableMultiAZ: 'true'
    tags:
      Environment: Production
      CostCenter: Engineering-Core
      ManagedBy: CloudFormationGitSync
```

#### When to Choose Git Sync vs. CodePipeline V2
- **Choose CloudFormation Git Sync:** Pure Infrastructure as Code repositories; teams wanting lowest operational overhead GitOps for CloudFormation stacks with zero pipeline maintenance costs.
- **Choose CodePipeline V2:** Multi-stage promotion pipelines (Dev -> Staging -> Prod) requiring automated integration tests, cross-account artifact promotion, container builds, or CodeDeploy canary/blue-green deployments.

## 2. AWS Cloud Development Kit (AWS CDK)

### 2.1 Construct Levels (L1, L2, L3)
1. **L1 Constructs (`Cfn*`, e.g., `s3.CfnBucket`):** Auto-generated 1:1 mappings of low-level CloudFormation resources. Require configuring every property manually.
2. **L2 Constructs (Curated AWS Constructs, e.g., `s3.Bucket`, `lambda.Function`):** Provide secure defaults, boilerplate abstraction, and intent-based helper methods like `bucket.grantReadWrite(myLambda)` which automatically generate least-privilege IAM policies and KMS permissions.
3. **L3 Constructs (Patterns, e.g., `ecs_patterns.ApplicationLoadBalancedFargateService`):** Combine multiple L2 constructs into complete, opinionated architectural patterns (VPC, ALB, Target Group, ECS Cluster, Fargate Service, IAM Roles, CloudWatch Log Groups) in a few lines of code.
   * **Escape Hatches (`node.defaultChild`):** When an L2 or L3 construct does not yet expose a newly released CloudFormation property, cast `construct.node.defaultChild as s3.CfnBucket` to access the underlying L1 construct directly or call `cfnBucket.addPropertyOverride('AnalyticsConfigurations', [...])`.

### 2.2 `cdk bootstrap` Architecture
Before deploying CDK stacks containing assets (Lambda zip files, Docker images) or large templates (>50 KB) into an AWS Environment (`aws://ACCOUNT_ID/REGION`), you must run `cdk bootstrap`. This provisions the **`CDKToolkit` CloudFormation stack** containing:
* **S3 Staging Bucket (`cdk-hnb659fds-assets-ACCOUNT-REGION`):** Stores CloudFormation templates and zipped file assets.
* **ECR Repository (`cdk-hnb659fds-container-assets-ACCOUNT-REGION`):** Stores Docker container image assets built by CDK.
* **SSM Parameter (`/cdk-bootstrap/hnb659fds/version`):** Tracks the bootstrap stack schema version (enforced via a CloudFormation `Rules` assertion in every synthesized template).
* **5 Standard Bootstrap IAM Roles:**
  1. `cdk-...-deploy-role`: Assumed by CDK CLI / CI/CD to invoke CloudFormation.
  2. `cdk-...-cfn-exec-role`: Passed to CloudFormation (`iam:PassRole`) to actually create/update stack resources (can be constrained with an IAM **Permissions Boundary** via `--custom-permissions-boundary`).
  3. `cdk-...-file-publishing-role`: Uploads zip assets/templates to the S3 staging bucket.
  4. `cdk-...-image-publishing-role`: Pushes container assets to the ECR staging repository.
  5. `cdk-...-lookup-role`: Performs read-only context lookups (`ec2.Vpc.fromLookup`).

```bash
# Bootstrapping a Production Target Account (222222222222) trusting the Tools Account (111111111111)
npx cdk bootstrap aws://222222222222/us-east-1 \
  --trust 111111111111 \
  --cloudformation-execution-policies arn:aws:iam::aws:policy/AdministratorAccess \
  --custom-permissions-boundary EnterpriseDeveloperBoundary
```

### 2.3 CDK Aspects (`IAspect` Visitor Pattern) & `CDK Pipelines`
CDK **Aspects** implement the **Visitor Pattern** across the entire construct tree during the `prepare` phase prior to CloudFormation synthesis.
* **Primary DOP-C02 Use Cases:**
  1. **Compliance Validation:** Inspect every `CfnBucket` or `CfnVolume` in a stack/stage and call `Annotations.of(node).addError("S3 Bucket must be encrypted!")` if non-compliant—which **aborts `cdk synth` and `cdk deploy` before touching AWS**!
  2. **Automated Mutation:** Automatically inject mandatory cost-allocation tags, KMS encryption, or IAM Permissions Boundaries onto every resource across hundreds of constructs without developers modifying individual L2/L3 construct code.

```typescript
import { IAspect, Annotations, Tokenization } from 'aws-cdk-lib';
import { IConstruct } from 'constructs';
import { CfnBucket } from 'aws-cdk-lib/aws-s3';
import { CfnRole } from 'aws-cdk-lib/aws-iam';

export class EnterpriseSecurityComplianceAspect implements IAspect {
  private readonly permissionsBoundaryArn: string;

  constructor(permissionsBoundaryArn: string) {
    this.permissionsBoundaryArn = permissionsBoundaryArn;
  }

  public visit(node: IConstruct): void {
    // 1. Validate that every S3 Bucket has versioning enabled
    if (node instanceof CfnBucket) {
      if (
        !node.versioningConfiguration ||
        (!Tokenization.isResolvable(node.versioningConfiguration) &&
          node.versioningConfiguration.status !== 'Enabled')
      ) {
        Annotations.of(node).addError(
          'COMPLIANCE ERROR: All S3 Buckets must have versioning enabled.'
        );
      }
    }

    // 2. Automatically attach the enterprise Permissions Boundary to every IAM Role
    if (node instanceof CfnRole) {
      node.permissionsBoundary = this.permissionsBoundaryArn;
    }
  }
}
```

* **`CDK Pipelines` (`pipelines.CodePipeline`):**
  * High-level L3 construct that creates a **self-mutating AWS CodePipeline**.
  * If you add a new application Stage, Region, or Account in your TypeScript/Python CDK code and `git push`, the **`UpdatePipeline` (Self-Mutate) stage** automatically reconfigures the CodePipeline itself and then deploys the newly added stages!

## 3. AWS Systems Manager (SSM) Deep Dive

### 3.1 SSM Agent, Hybrid Activations, & Private VPC Endpoints
* **Three Prerequisites for an EC2 Instance to Appear in SSM Fleet Manager:**
  1. **SSM Agent** installed and running (pre-installed on Amazon Linux 2/2023, Ubuntu 18.04+, Windows Server 2016+).
  2. **IAM Instance Profile** attached with the **`AmazonSSMManagedInstanceCore`** managed policy (do NOT use the legacy deprecated `AmazonEC2RoleforSSM` policy!).
     * *Tip:* Enable **Default Host Management Configuration (DHMC)** at the region level in Systems Manager (`AWSServiceRoleForAmazonSSM`) to automatically manage all EC2 instances via SSM without even needing to attach `AmazonSSMManagedInstanceCore` to every custom Instance Profile!
  3. **Outbound HTTPS (Port 443) Network Connectivity** to Systems Manager endpoints (via NAT Gateway or VPC Interface Endpoints).
* **Required VPC Interface Endpoints for Private Air-Gapped Subnets:**
  1. `com.amazonaws.<region>.ssm` (Core Systems Manager API control plane).
  2. `com.amazonaws.<region>.ssmmessages` (**Mandatory for Session Manager** interactive shells and port forwarding via WebSockets).
  3. `com.amazonaws.<region>.ec2messages` (Required by Run Command / State Manager on older agent versions).
  4. `com.amazonaws.<region>.s3` (**Gateway Endpoint** — required for Patch Manager yum/apt repo access, SSM Agent updates, and S3 log uploads).
* **Hybrid Activations (On-Premises Servers, VMware, Edge Devices, Other Clouds):**
  1. Create an IAM Service Role trusting `ssm.amazonaws.com` with `AmazonSSMManagedInstanceCore`.
  2. Create an **SSM Hybrid Activation** (`aws ssm create-activation`), which outputs an **Activation Code** and **Activation ID**.
  3. Install `amazon-ssm-agent` on the on-premises server and register it using the Activation Code & ID:
     ```bash
     # 1. Generate Hybrid Activation in AWS CLI
     aws ssm create-activation \
       --default-instance-name "OnPrem-DataCenter-AppServers" \
       --iam-role "SSMHybridServiceRole" \
       --registration-limit 50 \
       --expiration-date "2026-12-31T00:00:00Z" \
       --tags "Key=Environment,Value=HybridProd" "Key=Patch Group,Value=Prod-Linux"

     # 2. Register on the On-Premises Linux Server
     sudo amazon-ssm-agent -register -code "ACTIVATION_CODE" -id "ACTIVATION_ID" -region us-east-1
     sudo systemctl restart amazon-ssm-agent
     ```
  4. The on-premises server receives a managed instance ID prefixed with **`mi-`** (e.g., `mi-0123456789abcdef0`, whereas EC2 instances start with **`i-`**) and can now be patched, inventoried, and accessed via Session Manager identically to EC2!

#### CloudFormation Dynamic References (`{{resolve:...}}`)

* `{{resolve:secretsmanager:prod/aurora/creds:SecretString:password:AWSCURRENT}}` — Fetches a specific JSON key from an AWS Secrets Manager secret.

### 3.3 SSM Patch Manager Deep Dive
* **Patch Baselines:** Define which OS patches are approved for installation:
  * **OS-Specific:** Every operating system (`AMAZON_LINUX_2023`, `UBUNTU`, `RHEL`, `WINDOWS`) has an AWS Default Patch Baseline (e.g., `AWS-AmazonLinux2023DefaultPatchBaseline`), or you can create a **Custom Patch Baseline** and set it as default or associate it with a **Patch Group**.
  * **Auto-Approval Rules:** Filter by `Classification` (`Security`, `Bugfix`, `CriticalUpdates`), `Severity` (`Critical`, `Important`), and **`ApproveAfterDays: 7`** (waits 7 days after vendor release before auto-approving so patches can bake in Dev first!) or `ApproveUntilDate`.
  * **Compliance Severity:** Assigns `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, or `INFORMATIONAL` compliance failure severity when missing patches are detected in Systems Manager Compliance.
* **Patch Groups (Case-Sensitive Tag Trap!):**
  * Instances are mapped to a Patch Baseline using an EC2/SSM Tag with the exact key **`Patch Group`** (capital `P`, space, capital `G` — **case-sensitive**!).
  * Example: Tagging Dev instances with `Patch Group = Dev-Linux` and Prod instances with `Patch Group = Prod-Linux` allows you to associate a zero-day delay baseline (`ApproveAfterDays: 0`) with `Dev-Linux` and a 7-day delay baseline (`ApproveAfterDays: 7`) with `Prod-Linux`.
  * **Constraint:** A single Patch Group can be registered to **at most one Patch Baseline per operating system type**.
* **`AWS-RunPatchBaseline` Document & Maintenance Windows:**
  * `Operation: Scan` — Checks instance patch state against the Patch Baseline and reports compliance to SSM Compliance without installing anything or rebooting.
  * `Operation: Install` — Installs approved missing patches and reboots if `RebootOption: RebootIfNeeded` (default) is set (`NoReboot` defers reboot).
  * **Maintenance Windows:** Define a recurring cron/rate schedule, duration, stop-initiating cutoff, **Targets** (by `Patch Group` tag or Resource Group), and **Tasks** (Run Command `AWS-RunPatchBaseline`, Automation, Lambda, or Step Functions) with **`MaxConcurrency`** (e.g., `20%`) and **`MaxErrors`** (e.g., `5%`) rate controls.
  * **`PreInstallHookDocName` / `PostInstallHookDocName`:** `AWS-RunPatchBaseline` (and `AWS-RunPatchBaselineWithHooks`) allows executing custom SSM Command documents right before installing patches and right after rebooting to drain traffic or verify application health.

### 3.4 SSM State Manager, Session Manager, Distributor, Inventory, & AWS AppConfig

* **State Manager**
  * **Purpose & Architecture:** Continuous desired-state configuration engine. Runs SSM Command or Automation documents on a recurring schedule (`cron`/`rate`) against tagged instances and tracks **Association Compliance**.
  * **DOP-C02 Exam Scenario:** "Ensure `firewalld` is running and antivirus configurations are enforced every 30 minutes across 500 hybrid servers, and alert on configuration drift."
* **Session Manager**
  * **Purpose & Architecture:** Interactive browser/CLI shell (`aws ssm start-session`) and **SSH/Port Forwarding (`AWS-StartPortForwardingSessionToRemoteHost`)** using outbound HTTPS 443 to `ssmmessages`.
  * **DOP-C02 Exam Scenario:** "Provide audited shell access and port forwarding to a private RDS instance with **zero inbound security group ports (no port 22)**, no bastion host, no SSH keys, KMS encryption, and full session transcript logging to S3/CloudWatch."
* **Distributor**
  * **Purpose & Architecture:** Packages proprietary software agents (`.deb`, `.rpm`, `.msi`, zip) into SSM Packages and installs/updates them via `AWS-ConfigureAWSPackage` (often scheduled via State Manager).
  * **DOP-C02 Exam Scenario:** "Distribute and maintain a custom in-house security monitoring binary across Linux and Windows fleets."
* **Inventory**
  * **Purpose & Architecture:** Collects metadata on installed OS packages, applications, network configs, files, and Windows registry keys; syncs via **Resource Data Sync** to an **Amazon S3 bucket** for **Amazon Athena + QuickSight** SQL querying across all accounts!
  * **DOP-C02 Exam Scenario:** "Query which EC2 and on-premises servers across 50 accounts have `log4j` version `2.14.0` installed using SQL."
* **AWS AppConfig**
  * **Purpose & Architecture:** Managed runtime configuration & **feature flag deployment service** (part of Systems Manager). Decouples configuration updates from code deployments.
  * **DOP-C02 Exam Scenario:** "Roll out a JSON feature flag change to Lambda/ECS over 30 minutes, validate the JSON schema via **JSON Schema or Lambda Validator** before deployment, and **automatically roll back** if a CloudWatch Alarm fires."

## 4. AWS Elastic Beanstalk

### 4.1 Elastic Beanstalk Deployment Policies Comparison Matrix
Memorize this table for DOP-C02—Elastic Beanstalk deployment policy trade-offs (speed vs. cost vs. rollback vs. capacity) appear on almost every exam:

* **All at once**
  * **How It Works:** Deploys new version to all existing instances simultaneously.
  * **Service Downtime?** **YES** (Brief outage).
  * **Capacity During Deploy:** Drops to **0%**.
  * **Rollback Mechanism & Speed:** Must redeploy old version to all instances (Slow).
  * **Cost / Time Impact:** Fastest & $0 extra EC2 cost (Dev/Test only).
* **Rolling**
  * **How It Works:** Splits existing fleet into batches (`BatchSize`) and updates one batch at a time in-place.
  * **Service Downtime?** **NO.**
  * **Capacity During Deploy:** Reduced by **1 batch size** (e.g., 75% capacity).
  * **Rollback Mechanism & Speed:** Must perform another rolling update of old version (Slow, partial instances have mixed versions on failure).
  * **Cost / Time Impact:** $0 extra EC2 cost; moderate speed.
* **Rolling with additional batch**
  * **How It Works:** Launches 1 extra batch of new instances first, then performs rolling in-place updates, then terminates the extra batch.
  * **Service Downtime?** **NO.**
  * **Capacity During Deploy:** Maintained at **100%** throughout deployment.
  * **Rollback Mechanism & Speed:** Must perform another rolling update if later batches fail.
  * **Cost / Time Impact:** Minimal extra EC2 cost (1 batch during deploy).
* **Immutable**
  * **How It Works:** Creates a **temporary second Auto Scaling Group**, launches a full fleet of fresh instances with the new code, waits for health checks, moves them into the primary ASG, and terminates all old instances.
  * **Service Downtime?** **NO.**
  * **Capacity During Deploy:** Maintained at **100%** (briefly doubles to 200%).
  * **Rollback Mechanism & Speed:** **Instant & Clean:** If new instances fail health checks, Beanstalk simply terminates the temporary ASG—original instances were never touched!
  * **Cost / Time Impact:** Highest safety; doubles EC2 count temporarily; slowest deployment time.
* **Traffic splitting (Canary)**
  * **How It Works:** Launches a full new fleet of instances (like Immutable), shifts a small percentage (e.g., 10%) of ALB traffic for a configurable evaluation time (`EvaluationTime`), then shifts 100% and terminates old instances.
  * **Service Downtime?** **NO.**
  * **Capacity During Deploy:** Maintained at **100%** (doubles to 200% during test window).
  * **Rollback Mechanism & Speed:** **Instant:** Reverts ALB target group routing weights to original instances if CloudWatch/Health checks fail.
  * **Cost / Time Impact:** Best for production canary verification.
* **Blue/Green (External CNAME Swap)**
  * **How It Works:** Create a **separate Beanstalk Environment** (Green), deploy and test it independently, then invoke **Swap Environment URLs** (Route 53 CNAME swap).
  * **Service Downtime?** **NO.**
  * **Capacity During Deploy:** **200%** (Two full environments).
  * **Rollback Mechanism & Speed:** **Instant:** Swap Environment URLs back to Blue environment.
  * **Cost / Time Impact:** Required when updating RDS/Platform major versions or testing full environment changes.

### 4.2 Customizing Elastic Beanstalk: `.ebextensions` vs. `.platform/hooks`
On **Amazon Linux 2 / Amazon Linux 2023** platforms:
* **`.ebextensions/*.config` (Processed in alphabetical order, e.g., `01_packages.config`, `02_db.config`):**
  * `option_settings`: Configures Beanstalk namespaces (`aws:autoscaling:launchconfiguration`, `aws:elasticbeanstalk:application:environment`, `aws:elasticbeanstalk:command`).
  * `packages`, `groups`, `users`, `sources`, `files`.
  * **`commands` vs. `container_commands` (Classic Exam Distinction):**
    * **`commands`:** Run **BEFORE** the application and web server are set up and **BEFORE** the application version archive is extracted! They do not have access to your application source code.
    * **`container_commands`:** Run **AFTER** the application source code has been extracted to the staging directory (`/var/app/staging`), **BEFORE** the staging directory is moved to `/var/app/current` and the web server starts!
    * **`leader_only: true`:** Only valid inside `container_commands`. Guarantees the command executes on **ONLY ONE single instance** (the leader instance chosen by Beanstalk) during an environment deployment—**essential for running database schema migrations (`alembic upgrade head`, `rails db:migrate`, `flyway migrate`)** or seeding data so 20 instances don't run concurrent migrations!
  * `resources`: Provisions additional CloudFormation resources tied to the Beanstalk environment lifecycle (e.g., an ElastiCache cluster or SQS queue).
* **`.platform/hooks/` (Executable shell scripts with `chmod +x` for AL2 / AL2023):**
  * `.platform/hooks/prebuild/` — Runs before the platform builds/installs dependencies.
  * `.platform/hooks/predeploy/` — Runs after building dependencies in `/var/app/staging`, right before switching `/var/app/current` and restarting the application server.
  * `.platform/hooks/postdeploy/` — Runs after the application is deployed and running in `/var/app/current`.

```yaml
# .ebextensions/01_deployment_and_migrations.config
packages:
  yum:
    jq: []
    postgresql15: []

option_settings:
  aws:elasticbeanstalk:command:
    DeploymentPolicy: Immutable
    HealthCheckSuccessThreshold: Ok
    IgnoreHealthCheck: false
  aws:elasticbeanstalk:healthreporting:system:
    SystemType: enhanced

commands:
  01_tune_sysctl_pre_app:
    command: "sysctl -w net.core.somaxconn=4096"

container_commands:
  01_run_db_migrations_on_leader:
    command: "./scripts/run_migrations.sh"
    leader_only: true
```

### 4.3 Decoupling RDS from Elastic Beanstalk Lifecycle & Worker Environments
* **The Coupled RDS Trap:** If you create an RDS database directly through the Elastic Beanstalk Console/Configuration (`aws:rds:dbinstance`), the RDS instance is provisioned inside the Beanstalk CloudFormation stack. **Terminating the Beanstalk environment deletes the RDS database!** Even if you set `DBDeletionPolicy: Snapshot` or `Retain`, platform upgrades requiring Blue/Green CNAME swaps are still complicated by coupled databases.
* **Best Practice:** Always provision RDS **externally** (in a dedicated Data CloudFormation stack) and pass the connection endpoint, port, and Secrets Manager / SSM Parameter reference into the Elastic Beanstalk environment via environment properties (`aws:elasticbeanstalk:application:environment`) and Security Group ingress rules.
* **Web Server Environment vs. Worker Environment Tier (`cron.yaml`):**
  * **Web Server Tier:** Serves HTTP/S requests behind an ALB.
  * **Worker Tier:** Runs a background **SQS daemon (`sqsd`)** on each EC2 instance. `sqsd` pulls messages from an Amazon SQS queue (or reads periodic scheduled tasks from **`cron.yaml`** in the root of your source bundle) and sends an **HTTP `POST` request to `http://localhost:80/`** on the local instance! If the local worker web app returns `HTTP 200 OK`, `sqsd` deletes the message from SQS; if it returns non-2xx or times out, the message returns to the queue after `VisibilityTimeout` and eventually moves to the **Dead-Letter Queue (DLQ)**.

```yaml
# cron.yaml (Placed in root of Elastic Beanstalk Worker Tier source bundle)
version: 1
cron:
  - name: "hourly-invoice-reconciliation"
    url: "/tasks/reconcile-invoices"
    schedule: "0 * * * *"
  - name: "nightly-ledger-cleanup"
    url: "/tasks/cleanup-ledger"
    schedule: "30 2 * * *"
```

## 5. DOP-C02 Exam Traps, Anti-Patterns & Troubleshooting Runbooks

### 5.1 Top 10 Configuration Management & IaC Exam Traps
1. **Trap:** "Set `DeletionPolicy: Retain` on an RDS database so that if a developer changes the `DBInstanceIdentifier` during a CloudFormation stack update, the old database is not deleted."
   * **Reality:** `DeletionPolicy` only applies when a resource is removed from the template or the stack is deleted. When a property change triggers **Replacement** during an update, CloudFormation consults **`UpdateReplacePolicy`**! Set both `DeletionPolicy: Retain` and `UpdateReplacePolicy: Retain` (or `Snapshot`).
2. **Trap:** "Update the `Export` value in `NetworkStack` while `ApplicationStack` imports it via `Fn::ImportValue`."
   * **Reality:** CloudFormation strictly blocks modifying or deleting any exported output that is currently imported by another stack. Use **SSM Parameter Store** when cross-stack values need to be updated independently.
3. **Trap:** "Generate a new random `PhysicalResourceId` (such as a timestamp or UUID) in a Lambda-backed Custom Resource on every `Update` event."
   * **Reality:** Returning a different `PhysicalResourceId` on an `Update` tells CloudFormation that the resource was **replaced**, causing CloudFormation to immediately send a **`Delete` event with the old `PhysicalResourceId`** during cleanup! Keep `PhysicalResourceId` stable across updates unless you intentionally want replacement + deletion of the old physical resource.
4. **Trap:** "When an error occurs in a Custom Resource Lambda function, raise an unhandled Python exception (`raise RuntimeError(...)`) so CloudFormation immediately rolls back."
   * **Reality:** Raising an exception without sending an HTTP `PUT` (`Status: "FAILED"`) to the S3 pre-signed `ResponseURL` leaves CloudFormation waiting for up to **1 hour** before timing out! Always catch all exceptions and send `FAILED` to `ResponseURL`.
5. **Trap:** "Tag EC2 instances with `patch-group: prod` or `PatchGroup: prod` so SSM Patch Manager applies the Production Patch Baseline."
   * **Reality:** The SSM Patch Manager tag key is strictly **`Patch Group`** (exact capitalization and space). Any other spelling is ignored, causing instances to fall back to the default OS patch baseline.
6. **Trap:** "Run database migrations in Elastic Beanstalk using the `commands:` section of `.ebextensions` with `leader_only: true`."
   * **Reality:** `commands:` runs *before* the application source bundle is extracted, and `leader_only: true` is **only supported in `container_commands:`**! Always use `container_commands:` with `leader_only: true` for migrations that rely on application code.
7. **Trap:** "Deploy a CloudFormation StackSet that automatically provisions IAM baseline roles whenever a new account is created in an AWS Organization using `SELF_MANAGED` permissions."
   * **Reality:** Automatic deployment on account creation/OU join (`AutoDeployment: Enabled: true`) is **ONLY supported with `SERVICE_MANAGED` permissions** integrated with AWS Organizations.
8. **Trap:** "Wait for an EC2 instance in an isolated private subnet without IAM permissions to signal CloudFormation using `CreationPolicy`."
   * **Reality:** `CreationPolicy` (`cfn-signal --stack ... --resource ...`) calls the CloudFormation API and requires `cloudformation:SignalResource` IAM permissions. If the instance has no IAM permissions (or is an external/on-premises host), use a **`WaitCondition` + `WaitConditionHandle`**, which generates a pre-signed S3 URL requiring zero IAM credentials.
9. **Trap:** "Detect when an IAM SecureString parameter in SSM Parameter Store has not been rotated for 90 days using Standard Parameters."
   * **Reality:** Parameter Policies (`Expiration`, `ExpirationNotification`, `NoChangeNotification`) require **Advanced Parameters**.
10. **Trap:** "Prevent developers from deploying unencrypted EBS volumes across all deployment tools (Console, CLI, CDK) using `cfn-guard` in a single CodeBuild pipeline."
    * **Reality:** `cfn-guard` in CodeBuild only checks templates passing through that pipeline. To block non-compliant CloudFormation deployments account-wide regardless of how the stack is submitted, deploy a **CloudFormation Hook (`TargetPoint: PRE_PROVISION`, `FailureMode: FAIL`)** or an AWS Organizations Service Control Policy (SCP).

### 5.2 Quick Troubleshooting Runbook for CloudFormation & SSM Failures

* **Stack stuck in `CREATE_IN_PROGRESS` or `DELETE_IN_PROGRESS` for 60 minutes on a `Custom::*` resource**
  * **Root Cause:** Custom Resource Lambda crashed or timed out without sending `SUCCESS`/`FAILED` HTTP PUT to `ResponseURL`.
  * **Immediate Remediation:** Look up `StackId`, `RequestId`, `LogicalResourceId`, and `ResponseURL` in CloudWatch Logs for the Lambda execution, and manually run `curl -H "Content-Type: ''" -X PUT -d '{"Status":"FAILED",...}' "$RESPONSE_URL"` to unstick the stack immediately!
* **Stack stuck in `UPDATE_ROLLBACK_FAILED`**
  * **Root Cause:** A resource changed outside of CloudFormation (or a dependent resource was deleted/locked), preventing rollback to the previous state.
  * **Immediate Remediation:** Run **`ContinueUpdateRollback`** (`aws cloudformation continue-update-rollback --stack-name MyStack --resources-to-skip LogicalResourceId`) to skip the broken resource and return the stack to `UPDATE_ROLLBACK_COMPLETE`.
* **ASG Rolling Update fails with `Received 0 SUCCESS signal(s) out of 2`**
  * **Root Cause:** Instance `UserData` failed before `cfn-signal`, or instance lacks `cloudformation:SignalResource` IAM permission, or lacks outbound HTTPS to `cloudformation.<region>.amazonaws.com`.
  * **Immediate Remediation:** Check `/var/log/cloud-init-output.log` and `/var/log/cfn-init.log` on the instance; pass `$?` of `cfn-init` into `cfn-signal -e $?` so failures signal immediately instead of waiting for `PauseTime` timeout.
* **Private EC2 instance has `AmazonSSMManagedInstanceCore` and `ssm` VPC endpoint, but Session Manager fails to connect**
  * **Root Cause:** Missing **`com.amazonaws.<region>.ssmmessages`** Interface VPC Endpoint (or Security Group on VPC Endpoint does not allow inbound TCP 443 from the EC2 instance's subnet CIDR).
  * **Immediate Remediation:** Provision the `ssmmessages` (and `ec2messages`) Interface VPC Endpoints with Private DNS enabled and allow TCP 443 ingress on the endpoint Security Group.

## 6. Deep-Dive Whitepaper Patterns: Advanced IaC Governance & Extensibility

### 6.1 CloudFormation Custom Resource Internals & The 60-Minute Stack Freeze Trap

When extending CloudFormation using custom resources (`Custom::*` or `AWS::CloudFormation::CustomResource`):
- **Invocation Event:** CloudFormation invokes the backing Lambda function passing a JSON payload containing:
  - `RequestType`: `Create`, `Update`, or `Delete`.
  - `ResponseURL`: A pre-signed Amazon S3 URL generated by CloudFormation.
  - `StackId`, `RequestId`, `LogicalResourceId`, `ResourceProperties`.
- **The Expected Signal:** CloudFormation pauses stack execution until it receives an HTTP `PUT` request to `ResponseURL` containing a signed JSON document:
  ```json
  {
    "Status": "SUCCESS",
    "Reason": "Resource provisioned successfully",
    "PhysicalResourceId": "custom-resource-id-12345",
    "StackId": "arn:aws:cloudformation:us-east-1:111122223333:stack/...",
    "RequestId": "unique-request-id",
    "LogicalResourceId": "MyCustomDatabaseInitializer",
    "Data": { "Endpoint": "db.internal.corp" }
  }
  ```
- **The 60-Minute Freeze Trap:** If the Lambda function encounters an unhandled runtime error, crashes, runs out of memory, or exceeds its execution timeout *before* sending the HTTP `PUT` to `ResponseURL`, CloudFormation never receives a completion signal. CloudFormation waits **exactly 1 hour (3,600 seconds)** before timing out and failing the stack!
- **Staff-Level Architectural Defense:**
  - Always wrap custom resource execution inside a `try...except...finally` block (or use the AWS-provided `cfn-response` module).
  - In the `except` block, capture the error string and immediately dispatch a `Status: FAILED` payload to `ResponseURL` before exiting, allowing CloudFormation to trigger immediate rollback within seconds rather than freezing for an hour.

### 6.2 Proactive Enforcement: CloudFormation Guard Hooks vs Lambda Hooks

Unlike detective controls (AWS Config) that flag non-compliance *after* resources are created, **CloudFormation Hooks** intercept stack operations proactively:
- **Hook Lifecycle Points:** Hooks execute at `BeforeCreate`, `BeforeUpdate`, and `BeforeDelete` lifecycle phases.
- **Failure Modes:**
  - `FailureMode: FAIL`: Rejects the stack operation immediately if validation checks fail, blocking non-compliant infrastructure from ever being provisioned.
  - `FailureMode: WARN`: Logs warning messages in CloudFormation events but allows resource provisioning to proceed.
- **Guard Hooks (`AWS::CloudFormation::GuardHook`)**:
  - Purpose-built for declarative policy-as-code.
  - Directly evaluates **CloudFormation Guard (`cfn-guard`)** rule files stored in an S3 bucket against incoming template properties.
  - Native, managed, and requires **zero Lambda functions** or custom runtime maintenance.
- **Lambda Hooks (`AWS::CloudFormation::LambdaHook`)**:
  - Invokes an AWS Lambda function to execute imperative validation logic against third-party APIs or external CMDBs before resource creation.

### 6.3 Deterministic CDK Synthesis & `cdk.context.json` Governance

The AWS Cloud Development Kit (CDK) abstracts infrastructure as code, but dynamic lookups introduce non-deterministic risks:
- **Environmental Lookups:** Methods like `Vpc.fromLookup()`, `HostedZone.fromLookup()`, and `SSMParameterLookup` query live AWS accounts during `cdk synth`.
- **The `cdk.context.json` File:** CDK records the exact responses from these environmental queries in a local file named `cdk.context.json`.
- **Why Committing to Version Control is Mandatory:**
  1. **Deterministic Builds:** Committing `cdk.context.json` ensures that CI/CD build environments produce identical CloudFormation templates across different execution runs without querying live AWS APIs.
  2. **Credential Independence:** Automated CI/CD build runners (e.g., CodeBuild) can synthesize templates locally without requiring live AWS credentials or broad read permissions (`ec2:DescribeVpcs`, `route53:ListHostedZones`).
  3. **Drift Prevention:** Prevents accidental infrastructure destruction if external VPC subnets or route tables are modified out-of-band.

### 6.4 AWS CDK Aspects for Enterprise-Wide Compliance Enforcement

**CDK Aspects** implement the Visitor design pattern across the synthesized construct tree:
- An Aspect implements the `IAspect` interface and the `visit(node: IConstruct)` method.
- When `app.synth()` is invoked, CDK walks the entire construct tree and passes every construct node to the aspect.
- **Use Cases:**
  - Enforcing mandatory encryption across all `s3.CfnBucket` constructs.
  - Injecting required enterprise tags (`CostCenter`, `Environment`, `Owner`) across all taggable resources.
  - Enforcing TLS 1.3 on all load balancer listeners.
- **Scope Application:** Can be applied at the root `App`, specific `Stage`, or individual `Stack` via `Aspects.of(scope).add(new MyCustomAspect())`.

### 6.5 Stack Policy Overrides During Maintenance Windows

A CloudFormation **Stack Policy** protects stateful resources from accidental updates:
- By default, attaching a stack policy creates an implicit deny on all update actions for all resources unless explicitly allowed.
- During scheduled maintenance, an authorized engineer needing to perform an update on a protected resource (e.g., updating an RDS parameter group) should NOT delete the permanent stack policy.
- **Best Practice:** Pass the `--stack-policy-during-update-body` (or `--stack-policy-during-update-url`) parameter with the `aws cloudformation update-stack` CLI command. This temporary policy overrides the permanent policy **strictly for the duration of that single update operation**, restoring full protection immediately upon completion.
